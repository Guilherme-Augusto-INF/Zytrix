# 04 — Target Supabase architecture

## Principles

- Firebase remains the source/rollback system until explicit cutover approval.
- Browser code receives only the project URL and publishable key.
- Secret/service role keys exist only in controlled backend/ETL environments.
- Public-schema tables have RLS enabled and explicit grants.
- Private operational state lives in the non-exposed `private` schema.
- PostgreSQL constraints enforce structure; RLS authorizes rows; RPCs enforce atomic workflows; Edge Functions handle external secrets/webhooks.

## Components

| Need | Target |
|---|---|
| Identity/session | Supabase Auth |
| Email/password users | Official Firebase Auth export/import path using Firebase SCRYPT parameters |
| Google login | Supabase Google OAuth with verified-email/account-linking tests |
| Firebase UID preservation | `private.firebase_user_map` and `firebase_uid` migration columns |
| Relational data | PostgreSQL normalized tables |
| Row authorization | RLS + explicit column/table grants |
| Atomic domain commands | Restricted PostgreSQL RPCs |
| External payment/webhook secrets | Edge Function (not implemented until real provider exists) |
| Chat/live/poll durable updates | Realtime Postgres Changes |
| Viewer state | Realtime Presence plus server-owned heartbeat/session data |
| Reactions | short-retention records initially; Broadcast is the scale-up path |
| Files | Supabase Storage buckets and owner-path policies |
| Logs | `audit_logs`, function logs and platform logs without tokens/secrets |
| Schema versioning | ordered SQL migrations under `supabase/migrations/` |

## ID strategy

- Supabase Auth IDs are UUIDs and become internal relational FKs.
- Firebase Auth UIDs remain in a private one-to-one map.
- Firestore document IDs that are externally meaningful are preserved in `firebase_id` columns.
- Zytrix public account IDs remain in `user_accounts.zytrix_id`.
- New domain rows use UUIDs generated by PostgreSQL.
- ETL must resolve every Firebase UID before importing dependent rows; unresolved references are fatal reconciliation findings, not silently skipped rows.

## Realtime strategy

- Postgres Changes: lives, chat messages/settings, live bans, polls/options, support alerts, notification state and reward redemptions.
- Broadcast/Presence: private `live:<uuid>` topics, authorized through `realtime.messages` policies.
- Viewer count is derived from non-expired, server-owned sessions; total views increments once per authenticated user/live pair.
- Reactions remain short-lived and rate-limited. They can move fully to Broadcast when event volume justifies it.

## Storage strategy

| Bucket | Read | Write | Limit | MIME |
|---|---|---|---:|---|
| `avatars` | public | first path segment = authenticated user UUID | 2 MiB | JPEG/PNG/WebP |
| `channel-assets` | public | first segment = owned channel UUID | 5 MiB | JPEG/PNG/WebP |
| `live-thumbnails` | public | first segment = owned live UUID | 5 MiB | JPEG/PNG/WebP |

No `clips` bucket is created because the real product currently stores clip metadata only and has no video-generation/upload pipeline.

## Dual-run boundary

The preferred temporary model is read comparison, not indefinite dual-write:

1. Firebase remains authoritative during schema/ETL validation.
2. Reproducible full and delta exports feed Supabase staging.
3. The frontend migrates by service domain behind a backend selector.
4. Each migrated domain gets comparison telemetry and a rollback switch.
5. A short write freeze or deterministic final delta is required at cutover.
6. Dual-write, if temporarily required, must be idempotent and reconciled; it is removed immediately after cutover stability.
